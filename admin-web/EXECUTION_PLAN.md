## 2. 已定的工程方案

### 2.1 职责和改动位置

```text
Router / React adapter（页面、交互、焦点）
  → 领域 module 的 interface（读模型、编辑模型、校验、提交构造）
    → AdminApiClient（同源传输）
      → BFF（身份、来源、限流、签名）
        → mip-admin-api（授权、状态、事务、审计）
          → 既有领域函数 / 仓储 / ledger / outbox
```

`interface` 指调用方必须知道的完整使用约定；`seam` 是替换真实/测试 adapter 的位置。沿用现有 seam，不新建只做转发的层。测试通过与调用方相同的 interface 验证结果。

| 问题 | 本计划的实施选择 |
| --- | --- |
| 详情与编辑的数据形状漂移 | 每个对象只维护一份 DTO→编辑模型及编辑模型→提交输入转换，放 `src/modules`。React 不再用 `Record` 强转后猜嵌套路径，服务端必需字段缺失必须报读取错误，不能降为新建空表单。 |
| 同一 action 在弹窗和独立页重复处理 | 复用同一领域 validator/builder；独立页和弹窗仅是两个 React adapter。已有逻辑搬迁后删除旧实现及失效调用，不保留两套版本。 |
| 按钮规则在 UI 与服务端漂移 | 服务端是状态/权限事实源。逐对象扩展只读操作可用性投影（允许动作、禁用原因、可编辑字段），由同一服务端判断供 UI 消费；写入事务仍重新鉴权和校验，投影不充当授权票据。 |
| 查询、排序、分页、导出各写一套 | 每个领域有一个规范化查询输入，URL adapter 只序列化它；列表与导出使用相同过滤语义、时区和单位。排序放在分页之前执行，游标包含稳定次序。 |
| 通用表单泄露 ID/版本 | ID/版本/幂等键留在内部上下文；业务候选由授权范围内接口供给。只读字段和禁用原因明确，复杂合作卡使用领域编辑视图，保留公共字段/上传/反馈组件。 |
| 巨型聚合文件继续增长 | 沿本次功能逐步提取事件、机会、用户、任务等 module；旧总入口保留薄分派。不要全仓先搬家，也不以文件行数作为拆分目的。 |
| 缓存与多用户串数据 | 详情 key 含身份范围、对象 ID、分页/筛选；切账号/撤权清理受保护缓存。先保持既有成功写入后的广泛失效策略，建立依赖表并验证后才缩小失效范围。 |
| 多平台部署 | 前端始终同源；CloudBase/Cloudflare 差异留在认证存储、网关 adapter。业务修复不夹带域名、DNS、云资源退役或登录架构迁移。 |

不增加一个“万能后台 schema 引擎”。公共组件只承载布局、输入、加载和反馈，不认识 `mip.admin.*` action 或业务状态。

### 2.2 编辑保存的统一行为

1. 加载已有对象、校验必需结构、保存原始快照/版本，再生成编辑模型；默认值只用于新建或已确认可缺省字段。
2. 改动值与原始值按领域语义构造白名单输入。区分缺失、空文本、空列表、0、false，不能用 `||` 把合法值换成默认值。
3. 载入失败/对象不存在/权限变化时不能保存；切换对象后旧请求结果不能覆盖新表单。
4. 同一输入的重试使用同一幂等键，修改输入后使用新键；不自动重放未知结果的写入，先读取结果再决定下一步。
5. 版本冲突保留本地草稿和新服务端快照，由用户核对后再次提交；不能自动刷新表单清空用户刚输入的内容。
6. 成功后读取服务端事实并更新列表/详情。跨 Tab 编辑同一对象必须触发版本保护；不同对象不能共用一个草稿。

当前 `independent-form-page.tsx` 冲突分支会重新 `setFieldsValue`；W01 应覆盖“本地输入仍可找回”，不能只断言出现冲突提示。机会的 `opp.draft` 空回填是同类问题的首个回归样例。

### 2.3 契约、数据库和高风险角色改造

- 新增操作先改 `cloudfunctions/mip-admin-api/domain/operations/` 与实际 implementation，再运行 `node scripts/generate-admin-operation-contract.mjs --write` / `--check`。不手工修改生成清单；接口声明、返回成功或 operation 数量不等于实现。
- 中立共享类型仅放 `packages/admin-contracts`，已有 action/envelope 继续复用。需要共享的响应结构必须与真实服务端 fixture 做同一合同验证，不能只有 TS 类型和两套手写假数据。
- 优先扩展已有表；数据库变更追加 `database/mysql/mip/` 迁移并更新 lock。应用生成的 AppID 隔离变换、唯一键、外键与最小权限也要验证，不能只看旧 SQL 文本。不得修改已应用迁移。
- 先增加兼容字段/读取，再切换写入和页面；旧记录必须可读。回滚前端/函数时保留兼容数据；不使用删表、删除流水或重跑 seed 来“回滚”。
- **自定义角色不是把 `roles.create` 改成 INSERT 即完成。** 现有七种技术角色和 scope 受多处服务端校验，`mip_admin_roles` 目录目前并未打通实际授权。采用“系统角色作为权限上限 + 自定义岗位模板收窄权限 + 范围绑定”的方案，复用现有目录，不创建可任意提权的新字符串角色。
- W09 追加模板与绑定关联及基础角色引用，保留旧绑定兼容。有效权限取系统角色上限、既有角色策略、启用模板权限的交集；模板不存在/停用/非法时拒绝，不回退为系统角色全部权限。多绑定的合并仍逐范围执行，不能把城市 A 的权限套到城市 B。
- 平台超管仍为受保护系统角色，不能复制出第二种全权角色。普通模板只在授予者可授予的权限和范围内创建/绑定。不能让旧系统角色绑定残留导致“模板已收窄但仍有全权”；必须有绑定替换/重复授权检查及并发撤权测试。
- 角色改造必须盘点全部读取 `mip_admin_role_bindings` 的函数，包括 identity/events/tasks/media/game/banners、管理事务和 scheduler。读会话与事务内鉴权采用同一有效授权语义；函数继续自包含，不引入跨函数相对路径。纯授权合同如需生成到多个部署包，保留一个源及一致性检查，不复制后各自维护。
- 自定义角色分两步启用：所有消费者先部署能识别模板限制的兼容读取，确认读回后才开放模板绑定写入。旧后端忽略模板字段可能按基础角色放大权限，不能把这种旧版本作为启用模板后的回滚目标；回滚只能回到仍理解模板限制的版本，或停用该功能并保持拒绝，不降级成全权。

### W01 · 编辑 module 与保存安全

代码起点：`src/features/form-pages/`、`src/modules/content-form-values.ts`、`content-mutation-forms.ts`、`admin-event-mutation-forms.ts`、`src/shared/ui/operation-fields.tsx`；服务端机会 DTO 在 `domain/admin-prd-extensions.js`。
