## 1. 测试准备

### 1.1 角色口径（重要，先统一语言）

系统里**只有两种用户身份**，由服务端会员权益决定（`resolveUserKind`：有 ACTIVE 且在有效期内的权益 = 玩家）：

| 代号 | 角色 | 定义 | 展示 |
| --- | --- | --- | --- |
| R0 | 未登录游客 | 未完成微信登录/手机号授权 | 点受保护操作时弹半屏登录弹层 |
| R1 | 嘉宾 GUEST | 已登录、无有效会员权益 | 卡片/档案显示「嘉宾」 |
| R2 | 玩家 PLAYER | 持有 ACTIVE 会员权益（付费或后台补录） | 卡片/档案显示「玩家」+ Lv.N |
| R2p | 入会待审核 | 首笔付费已支付、后台未审核（PENDING） | 「入会审核中」，无玩家权益 |
| OP | 运营人员 | admin-web 账号（活动/内容/会员管理） | Web 后台 + 小程序现场工作台 |

**两个容易误解的口径：**
1. 「报名并签到一场活动后成为嘉宾」——签到**不改变全局身份**，它解锁的是**本场活动的互动权限**（活动反馈按钮、心动票）。登录后的非会员用户从头到尾都叫「嘉宾」。
2. 「机会模块只对玩家开放」——指**浏览列表**（项目机会 list、人才合作 list）是玩家权益；**发布机会**不限身份，所有登录用户都可以（含嘉宾）。

### 1.3 通用验收口径（贯穿所有用例）

- **服务端事实边界**：金额、报名资格、库存、签到资格、会员身份、可见性全部由服务端裁决；客户端只提交意图。任何「客户端自己算出来」的结果都是 Bug。
- **页面五态**：每个数据页检查 loading / 空态 / error / forbidden / conflict 的文案与恢复操作；装饰性请求失败不得让已成功的正文整页报错。
- **身份门禁顺序**：受保护动作按 `登录 → 协议 → 手机号 → 资料` 顺序逐步补全，补全后回到原意图继续；身份失败后的重试必须重新确认身份。
- **订阅授权形态（MIW-77 定稿）**：全 App **没有**自动弹出或常驻的订阅模块；原生订阅面板只在 3 个业务按钮的 tap 手势内拉起：「确认发布」（机会通知）、「提交报名」（活动提醒）、「我的 → 心动值入口」（心动提醒）。同一动作 24h 最多弹一次、拒绝后 24h 才再问、选「总是拒绝」永不再问；**拒绝订阅不拦截业务动作**。
- **站内信兜底**：所有通知站内信无条件落库；消息中心**进入页面即全部已读**（要观察未读红点，须先在「我的」页看）。

### 1.4 术语速查

| 术语 | 含义 |
| --- | --- |

### UF-01 管理后台创建活动 → 小程序「活动报名」列表出现（P0）

**角色**：OP1（后台）+ 任意小程序账号　**前置**：admin-web 已登录

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 | 后台 `#/events` → 新建活动：名称、富文本介绍（**插入一张图片**）、开始/结束时间、线下地点+城市、免费、自动确认、名额 20，保存为草稿 | 保存成功；列表出现 DRAFT 行；草稿可再次编辑回读一致 |
