# 通知投递合同

站内消息是用户可回查的权威事实，微信订阅消息、客服消息和服务号消息只是补充送达。业务事实与 `mip_inbox_messages`、`mip_delivery_tasks` 先提交；微信或 adapter 返回不能改变活动、订单、会员或运营发布状态。

## 投递阶段

`mip-notification-worker` 只在一段专用投递事务中调用微信接口。该事务用当前用户行锁与账号注销串行化，不能承载其他业务写入。每个任务按以下阶段处理：

1. reservation 短事务锁定任务与一条 `AVAILABLE` 授权，把授权改为 `RESERVED`，绑定 `reservation_task_id`、随机 token 和当前任务租约。唯一键保证同一任务只有一条保留授权，行锁和条件更新保证其他任务不能同时使用该授权。
2. reservation 提交后在进程内解密收件人并构造固定模板请求。收件人不进入 batch 响应、任务错误码或审计。本地校验失败时，fail 短事务把授权安全释放为 `AVAILABLE`。
3. 专用投递事务先以 `FOR UPDATE` 锁定收件人的 `mip_users` 行并确认仍为 `ACTIVE`，再锁定并复核任务租约、授权、`reservation_task_id` 和 reservation token。只有全部一致才调用微信；成功后在同一事务把授权改为 `CONSUMED`、任务改为 `DELIVERED`。该事务固定只尝试一次，避免数据库死锁重试自动重复外部调用。
4. 微信明确失败时，同一投递事务先写入任务失败和退避状态，再释放用户行锁。授权继续绑定原任务，只允许原任务重试；达到五次时改为 `EXPIRED`。进程中断或提交结论未知时，任务保持可恢复状态；最后一次租约过期后由 reaper 把授权改为 `EXPIRED`、任务保留为不可再领取的 `FAILED`，不转给其他任务。

账号注销会在同一注销事务内把 `AVAILABLE` / `RESERVED` 授权收敛为 `REVOKED`、清空 reservation 和加密收件凭据，并取消未完成任务。注销先取得用户行锁时，投递事务随后看到 `CLOSED`，不会调用微信；投递事务先取得用户行锁时，注销等待到微信调用及投递状态提交完成。由此可以证明“投递发生在注销之前”或“注销先完成并阻止投递”的顺序。

客服消息复用同一 reservation 和账号注销栅栏，但 48 小时交互窗口可重复使用：用户从正式客服入口进入会话后，用户态消息函数以可信微信上下文加密保存收件人，并由服务端设置过期时间；单条任务成功或明确失败后释放窗口，不把它当作一次性订阅授权。微信仍会按平台规则复核实际可发送窗口。

服务号渠道不把关注者 OpenID 写入 MIP 数据库。受控 HTTPS adapter 接收 AppID、内部用户引用、允许的模板、可信页面、字段和投递任务幂等键，用独立 HMAC 密钥验签后完成关注者映射与发送。adapter 缺失、模板未映射或密钥未配置时不创建外部任务。

## 用户偏好

评论通知和机会撮合通知默认开启，热点通知默认关闭。评论、撮合结果和热点内容 producer 只追加 outbox；投影时重新读取当前业务事实、有效用户、双向屏蔽和对应偏好。当前偏好关闭、事实已下架或来源版本已变化时，不创建站内消息或外部任务。用户偏好与微信订阅授权是两类事实：偏好决定是否应通知，订阅授权只决定某条已存在通知能否补充投递到微信。

## 外部调用边界

微信订阅消息和客服消息接口没有本项目可控制的幂等键，MySQL 提交也不能与微信接收组成原子事务。进程可能在微信已经接收请求、但投递事务提交前中断；租约恢复后原任务会重试，因此外部调用是 at-least-once，不是 exactly-once。服务号 adapter 接收固定任务 ID 作为幂等键，但该幂等只约束 adapter 自身。reservation 能防止授权或窗口被并发复用，用户行锁能与账号注销建立顺序，但二者都不能把微信外部副作用升级为数据库事务事实。

核心函数清单把通知 worker 和实际 sender 调用的硬上界固定为 60 秒，任务租约固定为 120 秒；正常云函数进程会在租约可被其他 worker 领取前结束。部署合同测试会阻止函数超时达到或超过任务租约。外部 provider 在进程终止后是否已接收请求仍不可证明，因此该时间边界不能升级为 exactly-once 保证。

`DELIVERY_OUTCOME_UNKNOWN` 表示无法证明外部调用结论。异常中心只返回脱敏状态；受控运营核对 provider 记录和站内消息后，才能决定是否创建新的业务通知。不得手工把 `RESERVED` 授权改回 `AVAILABLE`。

## 投递复核

消息活动派发和外部投递任务共用独立的复核工作流，但不复制或覆盖业务事实。`mip_message_delivery_reviews` 只保存来源引用、证据哈希、`OPEN | CLAIMED | RESOLVED`、15 分钟认领租约、处理结论和版本；当前任务、活动、授权及外部结论仍以各自业务表为准。已闭环记录只在新证据再次属于处理超时、结果未知或终止失败时重新呈现为待处理；后续成功或安全自动重试继续保持已闭环。同一来源行只反映最新复核状态，认领、核对和闭环由审计流水留痕，先前填写的说明与证据引用不作为列表历史保留。

只有平台负责人和平台运营通过 `messages.delivery.review` capability 才能调用管理端 v1 合同的 `list`、`get`、`claim`、`reconcile`、`resolve`。所有写操作都要求当前 `evidenceRevision`、`reviewVersion` 和 12–128 字符幂等键；相同幂等键只能重放相同请求。返回和审计只包含来源类型、状态、分类、证据版本和固定处理结果，不包含 OpenID、手机号、密文、消息正文、provider 原始响应或密钥。

`reconcile` 只按当前持久化证据收敛可证明的状态。消息活动可以根据现有派发事实完成、重新进入受控重试或继续隔离；投递任务通过 admin 到 worker 的独立 HMAC 调用处理过期 `PROCESSING`，不会调用微信 provider。`UNKNOWN` 和 `MANUAL_REVIEW` 绝不自动重放外部发送，也不能被改写成 `DELIVERED`。无法证明结论时，运营只能在认领后以 `UNKNOWN_NO_REPLAY` 加必填说明结束本次复核；这只关闭工作流，不伪造投递成功，也不创建新的业务通知。

没有既有复核记录的普通可重试失败继续留在自动投递通道，不进入人工复核列表。若运营认领后来源被正常 worker 收敛为成功或可重试状态，证据变化会要求重新认领；随后 `reconcile` 只把新证据保存为 `AUTO_CONVERGED` 并关闭复核，不再次执行活动发布或外部发送。

## 权限和运行

worker 仅通过内部 HMAC 调用，不开放客户端权限，不安装高频定时器。runtime MySQL 账号对 `mip_notification_grants`、`mip_delivery_tasks` 和复核工作流表只需要精确的 `SELECT`、`INSERT`、`UPDATE`，不需要 `DELETE`、schema-level 或全局权限。

模板、adapter endpoint、AppID allowlist、HMAC 和收件人加密密钥只放函数环境变量。手机号、OpenID、ciphertext、provider 原始响应和连接串不得写入响应或日志。

真机/生产仍需验证：真实模板字段、订阅授权一次性行为、客服会话窗口、服务号关注者映射、微信错误码、函数超时与租约间隔，以及“微信成功后投递事务提交结论未知”的恢复流程。
