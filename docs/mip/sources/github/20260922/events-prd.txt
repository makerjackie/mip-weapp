## 一、两分钟摘要

**目标**：活动模块所有页面的用户流程与交互，以本规格为准绳；实现侧按第五节偏差清单对齐。

**范围**：13 类屏幕/环节 —— 首页、详情、分享面板、报名（无独立表单屏，资料取自用户档案）、订单确认与支付、支付结果、扫码签到、参与人、现场互动（心动）、活动反馈、我的活动、订单列表/详情、现场工作台（管理员边界）。对应需求 B1–B8、C1–C8、D1–D8、F1、F5。机会广场、消息通知、个人档案不在本规格内。

**三个代表场景**：

1. **免费活动报名**：未登录用户从分享卡片进入详情 → 点报名 → 登录+补全 → 自动返回续报 → 提交成功（满员转候补）。
2. **付费活动报名**：已登录用户点报名 → 填表提交 →（订单确认页 *待裁决* ）→ 微信支付 → 支付成功才算报名成功；取消支付可重付。
3. **现场闭环**：扫码签到（未报名先报名）→ 已签到态解锁「与你互动」（心动限 1 票）与「活动反馈」→ 会后在「我的活动」取消报名（时限内，自动原路退款）。

**核心结论（3 条）**：

1. **主干一致**：实现的活动首页、详情、报名、签到、参与人、心动、反馈、我的活动、订单的结构与 PRD 主干一致，且 4 处实现比设计稿更完整（组合筛选面板、反馈/心动的签到拦截、详情页主按钮状态机、订单 4 Tab）。
2. **最大分歧**：付费报名是否存在独立「订单确认页」——设计稿有（购买须知/订单ID/价格明细/立即支付）、实现没有（表单提交后直接唤起支付）、PRD 未写。此为第七节裁决项 #1，另有 10 项裁决/确认项。
3. **实现必修 2 处**（与 PRD 直接冲突，无需裁决即可修）：联系电话配置值错误（18819253403 → 13798316515）；满员报名被拦时前端不透出「名额已满」原文。

## 二、角色与旅程总览

### 2.1 演员（按进入活动模块时的状态划分）

| 演员 | 进入状态 | 关键约束 |
| --- | --- | --- |
| 访客/未登录 | 未登录、未签协议 | 可浏览列表与详情；报名/签到动作触发登录+协议+资料门禁 |
| 已登录·未报名 | 资料完整 | 可报名；满员免费活动转候补 |
| 已报名 | 报名生效（免费即生效；付费以服务端支付确认为准） | 可扫码签到（现场） |
| 已签到 | ATTENDED | 解锁心动（限 1 票）与活动反馈 |
| 管理员 | 持 `events.checkin.manage` 等能力 | 专属现场工作台：生成/下载签到码海报；普通用户端无任何入口 |

### 2.2 旅程图

```
入口：Tab「活动」/ 发现页「更多活动」/ 分享卡片 / 邀请链接(i1.scene) / 扫签到码(s1.scene)
  │
  ▼
S1 活动首页（城市 + Banner + 报名/往期 Tab + 状态筛选 + 日期筛选 + 搜索 + 卡片流）
  │ 点卡片                                 └─ 「往期活动」Tab → 往期列表（回放卡）
  ▼
S2 活动详情（信息卡 / 指引 / 参与人预览 / 介绍 Tab / 底栏：客服·分享·主按钮）
  ├─「指引」→ 地图(openLocation / 复制地址)
  ├─ 客服 → 拨打 13798316515（*待改配置*）
  ├─ 分享 → S3 分享面板（微信 / 复制链接 / 下载二维码 / 文案）
  ├─「查看更多」→ S8 参与人
  └─ 主按钮（状态机）→ S4 报名（门禁 + 直报名，无独立表单屏）
        ├ 门禁：未登录/未协议/缺手机号/缺资料 → 登录补全 → 返回自动续报
        ├ 免费 → 提交 → 报名成功 / 候补 / 待审核
        └ 付费 → 提交 →（S5 订单确认页 *待裁决* ）→ 微信支付 → S6 支付结果
              ├ 成功 → 报名生效        ├ 取消/失败 → 待支付订单，可重付
              └（名额释放口径：退款成功后才释放）
活动日（现场）：
  微信内置「扫一扫」扫签到码（s1.scene）→ S7 签到（微信原生扫码，非小程序屏；未报名→引导报名后续签；识别失败→提示重扫；成功→已签到）
  已签到详情页：+「与你互动」区块 → S9 心动（本场限 1 票） ；+「活动反馈」→ S10 反馈（仅本场）
我的页：
  → S11 我的活动（待参加/已参加/历史 *Tab 数待裁决* ）→ 取消报名（时限内；原生 Dialog 确认）
       └ 付费 → 自动全额原路退款（既定口径）；名额退款成功后释放
  → S12 我的订单（全部/待使用/已完成/已退款）→ 订单详情 → 退款（原生 Dialog 确认）
管理员（admin 分包，普通用户不可见）：
  现场工作台 → 管理活动 → 活动现场 → 签到码海报（生成/保存相册/短时码）
```

### S1 活动首页

依据：B1–B8 ｜ `1819_17664_活动-首页-a`、`1820_19040_活动-首页-b`、`1824_19671_活动-首页-原生`、`1819_17793_活动-首页-日期选择`、`1819_17535_活动-时间选择`、`1819_18218_活动报名-已结束` ｜ TC-B-01~12

### S4 报名（无独立表单屏）

依据：C7、C10 ｜ **设计稿无报名表单屏**（「活动报名」屏实为订单确认页）｜ TC-C-10/11/15

> **2026-09-19 撤销**：原 S4 写有「报名资料卡（可改）→ 动态表单字段（后台配置：单行/多行/单选/布尔）」独立报名表单屏。经核对原始需求 C7（「已登录 → 直接报名成功」）与后台 PRD（活动管理 EV-01 无自定义报名字段配置项、EV-02 参与者管理无字段下发能力），该动态表单为无依据自拟，现予撤销。报名资料 = 用户档案资料（姓名/手机号），不设按场自定义报名问题。

**链路（撤销后）**：详情页点「立即报名」/「提交付费报名」→ 门禁（未登录/未签协议/缺手机号/缺资料 → 先补全，携带 REGISTER_EVENT 意图返回续报，C10 ✅）→ 通过后：

**动作表**：

| 触发 | 系统响应 | 结果/异常 |
| --- | --- | --- |
| 报名（免费） | 服务端校验名额/重复/资格 | 成功→报名即时生效（候补：已进入候补第 N 位；需审核：报名已提交）；重复→拦截 |
| 报名（付费） | 服务端创建待支付订单 | 进 S5（形态待裁决 #1） |
| 未登录/缺协议/缺手机号/缺资料 | 跳登录/补全，携带 REGISTER_EVENT 意图 | 返回后自动续报，上下文不丢（C10 ✅） |

**注意**：「在参与者列表展示公开资料」开关原挂报名表单，表单撤销后该开关归属用户档案/隐私设置——工作区已把该开关注释移除，移除后新报名用户默认不可见与否需产品确认（裁决 #9）。

### S5 订单确认与支付（⚠️ 核心裁决屏）

依据：C8 ｜ `1821_19274_活动报名`、`1723_16459_订单详情`（同构）｜ TC-C-12~14

**设计稿口径**：活动信息卡 →「购买须知」条款块 →「订单ID + 复制」→ 价格明细（多行：门票/周边/总计）→ 底部「¥合计 + 立即支付」。
**实现现状**：无独立确认页——报名（门禁通过）后直接 `payOrder` 唤起微信支付；订单确认版式仅作为 `figmaLayout:false` 的 fixture 存在。
**PRD 口径**：「付费活动点击报名后唤起微信支付」，未提确认页。

→ 裁决 #1（见第七节）。若采纳确认页，价格明细多商品行需要服务端订单模型支持（当前仅单金额 `amount_cents`）。

支付规则（既定）：`requestPayment` 成功 ≠ 报名生效，以服务端 ledger 确认为准；取消支付保留待支付订单（坐席保留 15 分钟），可重付；迟到支付自动转退款。

### S6 支付结果

设计稿无（断链）。实现已有 `payment-result` 页：成功 → 可看报名详情/我的活动；失败/取消 → 引导回订单继续支付。按实现保留，建议设计补稿（P2）。

**动作表**：

| 触发 | 系统响应 | 结果/异常 |
| --- | --- | --- |
| 微信内置「扫一扫」扫签到码（s1.scene） | 识别二维码 → 唤起小程序签到流程，校验活动码/有效期/报名资格/身份 | 成功→「签到成功」+「与你互动」入口（跳已签到态详情）；扫码 UI 为微信原生，非小程序屏 |

| 码无效/非本场 | 「未识别到有效活动码，请打开微信扫一扫重新扫码。」 | 不产生签到记录（D4/D5 ✅） |
| 重复扫码 | 幂等，提示已签到 | D6 ✅ |
| 非签到时间 | 服务端拒绝 | 现行口径=凭证窗口（开场前 6h~结束后 24h），与用例「活动起止」不符，**裁决 #10** |

## 六、设计稿自身问题备忘（开发勿照抄）

1. 占位数字不自洽：门票 ¥598+周边 ¥98=总计 ¥589（报名/订单详情两屏同错）；退款 ¥89≠实付 ¥589；「45参加/45/50/待参加(2)已参加(2)」互不对应；心动计数 3/23/99/566/12 全为占位。
2. 「我的订单-待使用/已完成/已退款」三屏页面标题误写「我的活动」。
3. 「活动详情-已签到」页标题错别字「以签到」。
4. 「活动-时间选择」屏并无时间选择器，实为“已按日期筛选”的列表态；「活动报名-已结束」屏并非报名已结束态（仅筛选 chip 换位且选中态仍是近期活动），命名错位。
5. 报名前详情稿含「活动反馈」入口，与「签到后才能反馈」规则表象冲突（本规格裁定：以 PRD 为准，签到后可见）。
6. 首页-日期选择稿：chip「2025.12.12」与日历「2026年2月」不自洽；分享卡「11.6」与「12月12日」并存。
7. 订单详情 Dialog 残留银行卡组件文案（「持卡人说明…」）为模板噪音。
