## 一、文档定位

本版本记录 2026-08-24 后台需求评审会议对 V0.4 原型 PRD 的对齐结论，作为后续开发依据：

1. 本文档中的规则与 V0.4 原型 PRD 冲突时，**以本文档为准**。
2. 本文档未提及的模块与细节（如首页仪表盘、运营管理、订单管理、战队管理、后台消息、服务器管理等），**沿用 V0.4 原型 PRD 不变**。
3. 开发优先级：**活动管理、机会管理**两个模块优先启动（见第七节）。

## 二、目标

- 建立一套轻量的 MIP 后台管理系统，支撑用户、活动、机会、成长体系（等级/经验值/贡献值）、任务、权益的日常运营管理。
- 通过本次评审消除原型与开发理解之间的歧义，使活动、机会两个模块可直接进入开发。
- 控制首期范围：奖金类权益仅线下发放、后台记录，不开发线上奖金功能。

## 四、后台基础规则

### 4.1 权限体系

**层级架构**：城市级 MIP 分会对应独立服务器，权限分为三级：

| 角色 | 定位 | 说明 |
|---|---|---|
| 总部超管 | 总部级别 | 拥有全部服务器、全部菜单权限 |
| 城市超管 | 城市级别 | 管理所属城市服务器，可按岗位细分授权 |
| 运营管理员 | 操作级别 | 由超管授权，仅可操作被勾选的菜单 |

**配置逻辑**：

- 权限不枚举细粒度规则，仅通过**勾选角色可操作的菜单范围**完成配置。
- 核心敏感权限（如**权益发放**）需严格管控，单独授权。
- 角色与权限的既有设计（菜单权限、操作权限、数据权限，不可删除已绑定角色等）沿用 V0.4 第 12 节。

### 4.2 账号绑定

- **不设置后台账号预注册流程**。
- 所有需配置后台权限的主体，**必须首先成为小程序注册用户**，在此基础上开通后台账号并绑定角色。
- V0.4 中「后台账号管理」的创建流程、双登录方式、状态与安全、审计日志等沿用不变。

### 4.3 通用配置与权益发放

| 配置项 | 规则 |
|---|---|
| 用户等级 | 后台自定义配置（沿用 V0.4「等级管理」） |
| 经验值 | 后台自定义配置规则与流水（沿用 V0.4「经验值管理」） |
| 贡献值 | 后台自定义配置规则与独立流水（沿用 V0.4「贡献值管理」） |
| 任务规则 | 后台自定义配置（沿用 V0.4「任务管理」） |
| 权益发放 | 支持**手动发放**、**系统发放**两种模式；后台留存**全流水记录** |
| 奖金类权益 | 一律**线下发放**，后台仅做信息记录；**首期不开发线上奖金功能** |

## 五、核心模块需求（本期开发重点）

### 5.1 用户管理

> 整体框架沿用 V0.4 原型，仅做少量细节调整；本节仅列出本次评审确认的调整项。

#### US-001: 用户详情独立 Tab 打开与多开对比

**Description**: 作为运营管理员，我希望用户详情页以独立浏览器 Tab 页打开，以便同时打开多个用户页面进行对比查看。

**Acceptance Criteria:**

- [ ] 用户列表中点击用户后，用户详情页以**独立 Tab 页**打开（非当前页跳转、非弹窗）。
- [ ] 支持**同时打开多个**用户详情页，各 Tab 数据独立加载、互不影响。
- [ ] 用户详情页整体框架沿用现有原型，仅调整本次确认的少量细节。
- [ ] 从用户详情页可正常返回用户列表，列表筛选状态不丢失。

**Functional Requirements:**

- FR-101: 用户详情页必须以独立 Tab 页方式打开，支持多开。
- FR-102: 多开的用户详情页之间数据相互隔离，刷新单页不影响其他页面。

### 5.2 活动管理

#### US-002: 活动标签管理

**Description**: 作为运营管理员，我希望维护活动标签的启用/停用状态，以便控制新建活动时可选择的标签范围。

**Acceptance Criteria:**

- [ ] 活动标签为**纯文本，限 5 字以内**；超过 5 字或含非文本内容时不允许保存并提示。
- [ ] 标签支持**启用/停用**状态切换。
- [ ] 标签停用后，**不再出现在新建活动的可选标签列表**中。
- [ ] 标签停用**不影响历史活动**已关联的标签数据（历史活动展示不变）。

**Functional Requirements:**

- FR-201: 标签名称限 5 字以内纯文本，保存时做长度与格式校验。
- FR-202: 标签支持启用/停用；停用标签对新建活动不可见。
- FR-203: 停用标签不改变历史活动的关联数据与展示。

#### US-003: 活动页面结构整合

**Description**: 作为运营管理员，我希望活动模块的页面结构更精简，以便减少冗余信息、聚焦运营操作。

**Acceptance Criteria:**

- [ ] 「报名与支付」与「参与人列表」**合并为一个模块**，报名、支付、参与者信息在同一处查看。
- [ ] 「活动反馈」**单独拆分为独立子模块**，支持查看与下载（沿用 V0.4 反馈能力）。
- [ ] **删除**邀请记录、签到记录等非必要字段/入口，相关页面不再展示。
- [ ] 原型页面结构按上述调整更新，其余字段沿用 V0.4。

**Functional Requirements:**

- FR-204: 合并后的「报名与参与人」模块可查看每场活动的报名信息、支付状态与参与者名单，并支持筛选、导出（沿用 V0.4 既有能力）。
- FR-205: 活动反馈作为独立子模块，与报名/参与人数据解耦。
- FR-206: 移除邀请记录、签到记录等冗余字段，不在后台展示与维护。

#### US-004: 活动创建与预览发布

**Description**: 作为运营管理员，我希望活动创建完成后先预览发布效果再发布，以便确认小程序端展示符合预期。

**Acceptance Criteria:**

- [ ] 活动创建完成后可**预览发布效果**（手机端预览，沿用 V0.4 预览弹层能力）。
- [ ] 场地跳转入口直接对接**已开发完成的 H5 页面**，后台无需额外开发相关功能。
- [ ] 预览确认后再执行发布，发布流程不需要审批（沿用 V0.1/V0.4 既有结论）。

**Functional Requirements:**

- FR-207: 活动创建/编辑完成后必须支持预览发布效果，预览通过后方可发布。
- FR-208: 场地跳转链接指向既有 H5 页面，后台仅做链接配置，不新开发场地功能。

#### US-005: 活动状态前后端对齐（跨端）

**Description**: 作为用户与运营管理员，我希望小程序端与后台的活动状态逻辑完全一致，以便避免状态歧义。

**Acceptance Criteria:**

- [ ] 小程序端补充**「下架」**状态展示与处理逻辑。
- [ ] 前后端活动**状态枚举完全对应一致**，不存在单端独有的状态。
- [ ] 活动被后台下架后，小程序端及时同步展示对应状态。

**Functional Requirements:**

- FR-209: 统一活动状态枚举（含已发布、已结束、已取消、下架等），小程序端与后台共用同一套状态定义。
- FR-210: 后台下架操作必须同步生效到小程序端。

### 5.3 机会管理

#### US-006: 机会列表筛选

**Description**: 作为运营管理员，我希望按多维度筛选机会列表，以便快速定位目标机会。

**Acceptance Criteria:**

- [ ] 支持按**主营城市**筛选。
- [ ] 支持按**发布人**筛选。
- [ ] 支持按**时间范围**筛选；时间筛选组件统一使用**含常用默认值的通用组件**（与全后台一致）。
- [ ] 支持按**自定义金额范围**筛选（最小值–最大值自填）。
- [ ] 筛选条件支持组合使用，结果正确。

**Functional Requirements:**

- FR-301: 机会列表支持主营城市、发布人、时间范围、自定义金额范围的组合筛选。
- FR-302: 时间筛选使用全后台统一的时间筛选通用组件，内置常用默认值（如今日/本周/本月）。

#### US-007: 机会状态操作

**Description**: 作为运营管理员，我希望明确哪些状态的机会可在后台操作，以便规范运营动作。

**Acceptance Criteria:**

- [ ] 仅**「招募中」**状态的机会支持后台操作（如编辑、下架等）。
- [ ] 非招募中状态的机会仅可查看详情，不提供操作入口。

**Functional Requirements:**

- FR-303: 后台操作按钮仅对「招募中」状态的机会开放；其他状态只读。

#### US-008: 机会导出

**Description**: 作为运营管理员，我希望将机会项目全字段详情导出为 Excel，以便线下分析与管理。

**Acceptance Criteria:**

- [ ] 导出内容为**项目全字段详情**，生成 **Excel 文件**下载。
- [ ] 导出遵循当前筛选条件与权限范围。
- [ ] 翻页组件**沿用现有固定方案**，不新开发翻页组件。

**Functional Requirements:**

- FR-304: 导出功能输出包含机会全字段的 Excel 文件，字段与列表详情一致。
- FR-305: 列表翻页沿用现有固定翻页组件方案。

## 六、UI 优化（侧边栏）

- **调整范围**：现有后台组件、交互逻辑**全部保持不变**；仅将**侧边栏**调整为参考 Pinterest 获取的**蓝色风格**样式，其余部分无需改动。
- **落地流程**：

1. 相关负责人输出侧边栏调整**原型**；
2. 确认效果符合预期后，再正式落地开发。

**Functional Requirements:**

- FR-401: 侧边栏视觉样式调整为蓝色风格（参考 Pinterest 素材），菜单结构、交互逻辑不变。
- FR-402: 除侧边栏配色外，不得引入任何其他 UI/交互变更。

## 八、扩展功能规划（开放 API）

- **需求背景**：后续系统开源需开放**经验值、贡献值的 API 接口**，支持外部系统对接调用，满足第三方共建需求。
- **能力设计**：接口支持配置**操作权限**与**数值范围限制**。
- **开发安排**：具体规则暂未明确，**按需开发**，不纳入首期范围；架构上预留扩展点，不会大幅增加开发成本。

## 九、Non-Goals（明确不做）

- **不做线上奖金功能**：奖金类权益一律线下发放，后台仅做信息记录（首期）。
- **不设后台账号预注册流程**：后台账号必须先为小程序注册用户。
- **不做细粒度权限规则引擎**：权限仅按菜单勾选范围配置。
- **不新开发场地相关后台功能**：场地跳转复用已完成的 H5 页面。
- **不保留邀请记录、签到记录等冗余字段**：从后台删除。
- **不改动侧边栏以外的 UI 与交互**。
- **不新开发翻页组件、时间筛选组件**：均复用现有/通用方案。
- 开放 API（经验值/贡献值）首期不开发。
