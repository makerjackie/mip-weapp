- 编辑已发布活动、复制历史活动：合法字段和动作正确，版本冲突可恢复；复制必须重新填写标题和开始/结束日期时间。

### 必须保住的活动联动：W05，E06–E09

报名/支付合并名单、反馈、导出、签到码与刷新吊销、活动统计、权限/审计，以及小程序对活动内容的读取都属于活动模块联动复验范围。禁止为了对齐创建页删除这些能力。真机项和依赖未决业务规则的项分开列状态，不跳过后写成“活动全部正常”。

### 额外问题：退款入口与状态提示

用户本次报告的“提交退款 → 当前状态不支持此操作”须定位并修复确定的界面/状态判断缺陷，详见 §6。退款资格和财务流水不能为完成本轮 UI 而放宽。涉及尚未批准的退款例外，引用 Q-ADMIN-03 等当前业务决定并明确等待项。

本期不要求重做整套后台。测试报告仍要列出全部可见模块的状态：受共享组件/契约影响的功能做回归；未测、超出本期或缺准备的项目明确标注，不能由页面冒烟外推为全后台业务验收通过。

## 6. 退款报错交接

### 用户报告，待独立复现

页面“提交退款”，提示“提交当前订单的退款申请。金额和退款状态由服务端订单与支付流水决定。”填写退款原因后出现：

> 当前状态不支持此操作
> 请求结果不确定时，请先刷新并核对服务端记录。

目前没有内部订单 ID、当时订单/报名/签到/退款状态、角色范围或网络响应，不能仅靠掩码订单号认定根因，也不把用户展示的报错当作一次获授权退款指令。

### 源码核对线索

- `admin-detail-actions.tsx` 已按 `availableRefundActions` 决定是否显示退款按钮；并非完全没有状态判断。
- `domain/orders.js` 的投影判断权限、订单状态、已退款金额、内容退款资格等；`domain/repositories/orders.js` 写事务对活动单还检查报名记录与有效签到，存在额外的 `INVALID_STATE` 拒绝条件。
- 以上说明需要核对“入口投影 / 选单 / 事务当前事实”是否一致；不能证明用户这一次就是签到导致。也要排查打开弹窗后状态改变、处理中的退款和资格窗口。

### 实现与测试要求

1. 从获授权的订单详情确认该单类型、状态、已有退款、报名/签到及权限；敏感标识只放本机测试映射，不放 Git 或报告。
2. 合法可退单应有正确入口；不可退单给具体原因，避免让用户填完表单才遭必然拒绝。用相同服务端规则投影可操作性，事务仍重新鉴权/核对状态。
3. 状态/资格拒绝、权限拒绝与真正网络未知结果分开呈现。弹窗打开后状态发生变化，保留原因输入，刷新订单事实并说明下一步。
4. 退款金额由订单快照和流水计算；不加任意金额输入、不把状态改回 PAID、不跳过签到/退款规则、不删除已有退款记录。
5. 合法成功、不可退、退款处理中、重复提交、资格过期、撤权、已签到活动单均有覆盖；失败不能多写退款或改变权益/报名。
6. 真实支付/退款由用户完成最终财务动作或另按明确授权执行；本期可先用测试 adapter/获准隔离环境验证状态机。未完成真实资金链路时，报告必须保留限制，不写“真实退款通过”。

## 7. Codex 独立测试方式

| 小程序与真机 | 开发者工具核对对应图文/状态；手机号、扫码签到、支付、相册等真机验收 | 开发者工具 `login:false` 不是登录成功；预检不是手机验收；AI 自动化也不是 Kingsley/Ame 的人工验收 |

视觉检查覆盖 **1440×900、1280×720、390×844**。记录实际 CSS viewport，不能只记请求值；窄屏根页面无横向溢出，表格自身滚动允许。对比原型与实现的层级、字段顺序、主操作、工具栏、媒体和手机预览，不拿随机像素相似度作为唯一结论。

测试写入只用单独标记的测试对象，记录创建/修改范围和可恢复清理方法。不发布给真实用户、不发送通知、不退真钱、不改真实角色/凭证、不删除业务数据来完成测试。缺测试账号/角色/数据、服务权限或真机条件时列为 `BLOCKED` / `WAIT_MANUAL`，继续其他不依赖该条件的检查。凭证只从获授权本机配置或用户授权流程取得，不能写入文档、源码、截图或日志。

### 发布前交给 Codex 的最小信息

- 实现 commit SHA、分支、精确变更文件和 PRD/标准映射；未做或受限项目。
- 测试及门禁运行结果，migration（如有）与回滚边界。
- 已部署 origin、部署时间、前端资源清单与函数版本，或者明确 `LOCAL_ONLY`，不要把本地实现当线上完成。
- 测试账号角色和范围的别名映射、数据准备与清理说明；密钥经本机安全配置，不在交接文本中交付。
- 使用有格式的图文、图片及长标题等复现数据；历史纯文本/旧图片样本；合法/非法状态和角色夹具。
- 给测试者的可复现操作步骤和已知限制；所有测试写入可能触发的发布、通知、资金或权限副作用。

## 8. 交付报告与退回规则

按 [报告模板](REPORT_TEMPLATE.md)提交结果，至少包含：

1. 被测版本与原型/PRD来源，测试环境和证据采集时间。
2. 原型和实现的同区域截图对照；桌面/手机、创建/编辑/预览/列表/设置，指出具体差异与影响。
3. 每条功能用例的预期、实测、`PASS / FAIL / BLOCKED / WAIT_MANUAL / NOT_RUN / OUT_OF_SCOPE`、截图/脱敏回读/文件证据；覆盖率给分母，不把不可执行当通过。
4. 缺陷严重度、复现步骤、影响、实施者修复提交、Codex复测结果；退款报错单独追踪。
5. 全部可见模块的回归状态及未测范围，测试对象残留、回滚/生产风险和最终人工结果。

有核心创建/保存/预览/发布断点、数据丢失、权限/金额错误，或 P0 用例失败时退回实现 AI。对核心用例仍 `BLOCKED` / `NOT_RUN` 的版本不给“可用”结论。只有本期必需功能有证据通过、阻塞缺陷闭环后，才能说“本期活动功能已通过已列测试”；完整产品/真机/资金仍未验证时必须在同段说明。

目标是按列明范围完成验证，不作脱离版本、环境和用例的“所有功能永远正常”保证。
