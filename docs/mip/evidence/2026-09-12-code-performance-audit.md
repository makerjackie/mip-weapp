### 切页后加载专项修复

- 活动和机会的公开列表请求不再预先下载整个响应中的云图片。首页与两个列表页先拿到标题、时间、地点等业务字段；既有卡片组件再独立补齐封面与头像，继续使用原生云下载和原有占位图、尺寸、样式。
- 卡片复用或销毁后忽略旧图片响应，避免快速切换筛选时错图或向已销毁组件写数据。列表分享在封面仍为云文件 ID 时使用默认分享截图，不向分享接口传入未解析地址。
- 下载增加全局 3 并发上限，保留同文件合并和缓存；阻塞业务数据的图片请求优先于卡片后台图片排队。尚未完成的原生下载不能取消，当前仍可能占据下载槽位。
- 新增仅驻留本机内存的最近 100 条耗时记录。`getApp().getLoadingDiagnostics()` 返回 `events.request`、`opportunities.request`、`identity.request`、`banners.request` 与 `media.download` 的起点、时长和 Promise 是否正常完成；`getApp().clearLoadingDiagnostics()` 清空记录。没有请求参数、响应正文、图片地址或用户标识，也不上传日志。
- `*.request` 包含 CloudBase 初始化、网络往返和重试退避，**不是云函数服务端执行时间**；`media.download` 包含图片排队、下载与重试，正常完成也可能留下坏图占位。不同记录可能并发，不能直接把所有时长相加当作首屏耗时。
- 活动详情页后续已单独启用渐进补图；其他详情调用方、身份头像、Banner 和其他模块仍保留原有图片解析路径，没有全局改写图片展示。其实际耗时需从新版真机记录继续定位。

## 慢在哪里

1. [导航封装](../../../src/platform/navigation/client.ts)直接调用 `wx.switchTab` / `wx.navigateTo`，没有统一的导航前云请求。部分受保护入口主动刷新身份，这与 Tab 切换需要区分。
2. [活动页](../../../src/pages/events/index.ts)原首屏链路是“身份 → 分会 → 筛选目录 → 列表/Banner”。身份与分会存在数据依赖，本轮保留；移除了无筛选时不必要的目录等待。
3. [个人页](../../../src/pages/profile/index.ts)刷新身份后并行读取分会、行业、成长、徽章、合作卡、案例、机会、影响力和未读消息。原首屏等待所有请求；现在主内容与区块完成状态分开。
4. [图片解析](../../../src/platform/storage/cloud-media.ts)原来在云函数响应后，下载响应中全部未缓存 `cloud://` 文件，单批最多并行 3 张，每张失败可重试一次，然后才返回页面数据。这段耗时属于图片下载与客户端编排，不是云函数执行时间。后续专项修复已将活动/机会列表及活动详情页改为先返回业务数据，再补图片；其他接口保留原路径，真机展示兼容性和实际收益仍待验收。
5. [读取重试](../../../src/shared/retry.ts)最多执行 5 次，额外退避合计 4850 ms，另加每次调用本身的耗时。只在 transport 抛错时触发，不能把这 4850 ms 当作正常请求耗时。本轮没有移除错误恢复机制。
6. 云端 MySQL adapter 已复用模块级连接池，身份 `loadFacts` 已并行读取多组事实；没有证据支持“每次切页都重新创建数据库连接池”。函数冷启动、数据库恢复、网络或具体 SQL 耗时仍需实测，不能据此排除云端问题。
