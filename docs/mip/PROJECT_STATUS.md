# MIP 当前进度与缺口

更新日期：2026-08-25。

本文记录当前仓库的可验证事实，避免把“已有代码”“本地测试通过”“开发者工具可打开”和“产品完成”混为一谈。需求定义见 [REQUIREMENTS.md](REQUIREMENTS.md)，逐项状态见 [COVERAGE_MATRIX.md](COVERAGE_MATRIX.md)，验收证据见 [ACCEPTANCE.md](ACCEPTANCE.md)。

## 结论

当前仓库已经具备较完整的服务端领域、数据库隔离、权限、审计和小程序页面骨架，不适合推倒重写。当前主要问题是覆盖面很广，但真实业务数据、管理员身份、真机能力、正式外部配置和跨端闭环没有形成足够的产品验收证据。

独立网页管理后台尚未实现，且不属于当前阶段目标。当前推荐把“小程序管理分包 + `mip-admin-api`”建设为手机与微信电脑端共用的正式管理产品，同时保留未来网页后台可复用的服务端契约。

## 已形成较强基础的部分

- 用户、玩家/嘉宾、城市分会、会员权益、订单、活动、机会、成长、任务、游戏化、知识内容和消息已经形成服务端事实模型。
- 玩家资格、金额、报名、签到、成长余额和权限不由客户端决定。
- 平台、城市分会、活动三级范围和七类管理角色已有 capability、事务内重授权和审计实现。
- `mip_*` 表、`mip/` 对象路径、函数名和部署清单已经与共享环境中的其他项目隔离。
- 支付 ledger、退款、outbox、站内消息和媒体安全已有代码与聚焦测试。
- 小程序“我的、活动、机会”已有 Figma 节点映射和本地设计资产。

## 尚未完成或证据不足的部分

### 产品运行时

- 当前微信身份尚未完成协议、档案、玩家和管理员完整条件，管理页面没有正常业务态验收。
- 分会、玩家、嘉宾、活动、报名、机会和订单已有可重复演示夹具；当前微信身份仍缺可重复管理员授权链路。
- 活动、机会、订单、知识等详情页面大量停在空数据或无权限状态。
- Figma 代表 frame 已固定，但尚未完成同尺寸运行截图与逐屏视觉差异验收。

### 真机与正式环境

- 手机号、扫码签到、相册、地图、日历、录音、私密视频号和 `web-view` 仍需真机。
- 正式 AppID、支付商户、回调、退款、通知模板和 AI provider 尚未完成生产验收。
- 正式协议、城市/行业目录、等级规则、勋章、游戏规则、知识内容和价格仍是可替换配置。

### 明确功能缺口

- 管理分包尚未完成手机/电脑双端响应式壳层、宽屏信息密度和真实 Windows/Mac 微信验收。
- 活动详情已接入活动评论用户闭环，包含分页查看、身份门禁、内容安全、限时编辑、软删除、举报、双向屏蔽和评论关闭状态；仍需在微信开发者工具完成运行时验收。
- 网页后台原型新增的后台账号、手机号验证码/密码登录、服务器概念、短信通知、活动复制、手机预览、定时消息和发送失败重试等能力尚未完成对齐。

## 定向重构范围

不做整体重写，只处理会阻碍后续并行开发的结构问题：

1. 提取渠道无关的管理合同，当前 CloudBase transport 和未来 HTTP transport 使用同一组 DTO、错误码、capability 和版本规则。
2. 将 `mip-admin-api` 中超大的 repository/service 按用户、活动、订单、权限、消息和知识拆成内部深模块，但保留一个部署单元。
3. 当前微信身份 adapter 进入统一 trusted principal 与 RBAC；未来如建设网页，仅新增 Web principal adapter。
4. 逐步收拢小程序页面直接调用浅层 gateway 的情况；不为重构而一次性改写所有页面。
5. 审核未注册到 `src/app.json` 的旧页面和旧 `src/modules/membership`，确认无有效入口后再删除，避免虚假覆盖和维护负担。
6. 重新区分 `implemented-local`、`partial-local`、`external-wait` 和 `unimplemented`，禁止用页面文件或测试数量冒充产品完成。

## 当前优先级

1. 固定内部需求、冲突和待确认问题。
2. 建立可重复的真实测试身份和业务夹具。
3. 建立渠道无关管理合同和手机/电脑响应式管理壳层。
4. 完成第一个可测试的用户管理与免费活动纵向切片。
5. 根据真实反馈再并行扩展支付、机会、成长、任务、游戏化、知识和消息。
