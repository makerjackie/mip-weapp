# MIP 当前进度与缺口

更新日期：2026-08-27。

本文只记录当前仓库可验证的事实，避免把“已有代码”“本地测试通过”“开发者工具可打开”和“产品验收完成”混为一谈。需求定义见 [REQUIREMENTS.md](REQUIREMENTS.md)，逐项状态见 [COVERAGE_MATRIX.md](COVERAGE_MATRIX.md)，验收证据见 [ACCEPTANCE.md](ACCEPTANCE.md)。

## 结论

当前仓库已经具备会员、活动、机会、成长、内容、消息、订单、支付与运营管理的完整技术底座，不适合推倒重写。现阶段的主要缺口不是继续横向增加页面或重新设计管理 API，而是补齐可重复 Demo 数据、对 108 条路由做代表性手机与电脑宽屏复验，并收口第一条真实业务闭环。

独立网页管理后台不属于当前交付目标。当前产品形态是“小程序用户端 + 小程序管理分包”，管理分包同时适配手机和微信 Mac/Windows 宽屏；服务端保持渠道中立，未来如确有需要再增加 Web principal 与 HTTP transport。

- 当前微信身份已完成协议、档案和手机号绑定，并精确初始化为唯一 `PLATFORM_OWNER`；手机号原值不写入仓库。
- 管理端已经使用渠道中立的 DTO、错误合同、trusted principal、transport 和 145-action operation registry。
- 事件复制、未保存草稿手机预览、用户内容治理、统一权益台账、支付尝试记录、消息投递记录、消息模板、定时发送和失败复核已有本地实现与聚焦测试。
- 管理端已有三档响应式壳层；仪表盘指标和订单、报名、参与者三张高密度页面已完成专门的宽屏可读性修复。
- `mip_*` 表、`mip/` 对象路径、函数名和部署清单已与共享环境中的其他项目隔离。
- 支付 ledger、退款、outbox、站内消息和媒体安全已有代码与聚焦测试。

## 尚未完成或证据不足

### 产品运行时

- 当前 108 条路由需要代表性手机与 960px+ 复验，6 个交互旅程需要重新生成严格报告；旧 95 路由报告不得继续引用为当前结果。
- 当前 Owner 是管理员，但不等于有效付费玩家；玩家专属页面仍需要有效 TEST 权益或另一名合法测试账号。
- 固定 Demo 数据已扩展到分会、用户、会员、订单、活动、报名、机会、合作卡、案例、公告、知识、消息、任务、成长、赛季、排行和盲盒，并已在当前 development 环境幂等写入和计数复核。Banner 正常态仍需要一张通过媒体安全检查的真实云素材；异常中心按现有失败投递事实展示，不伪造支付或 provider 故障。
- 管理仪表盘 375px 已有真实业务态截图；原 1024px 截图暴露过窄指标卡并已触发代码修复，但修复后的 960px+ 运行截图仍待重取。
- Figma 代表 frame 已固定，仍需同尺寸运行截图与逐屏差异验收。

### 真机与正式环境

- 手机号授权/换绑、扫码签到、相册、地图、日历、录音、私密视频号和 `web-view` 仍需真机。
- 正式 AppID、支付商户、回调、退款、通知模板和 AI provider 尚未完成生产验收。
- 正式协议、城市/行业目录、等级规则、勋章、游戏规则、知识内容和价格仍是可替换配置。
- scheduler 代码已完成；自动创建专用 CAM 角色仍被腾讯云 `CreateRole` 权限阻塞，不影响其余代码与本地验收。

## 定向重构范围

不做整体重写，只继续处理会阻碍并行或维护的深模块问题：

1. 保持现有渠道中立管理合同稳定；未来 Web 只增加 principal/transport，不复制业务规则。
2. 将 `mip-admin-api` 过大的 repository 按用户、活动、订单、权限、消息和知识逐域抽成内部深模块，保留一个部署单元和 145 个公开 action。
3. 页面继续只经过 modules 与 platform；不在页面复制资格、金额、权限和状态机。
4. 审核未注册页面和旧模块时先证明无有效入口，再做删除，避免用清理制造回归。
5. 持续区分 `implemented-local`、`external-wait`、运行证据和生产证据，禁止用文件或测试数量冒充产品完成。
