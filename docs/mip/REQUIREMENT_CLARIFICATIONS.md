# 需求澄清记录

这里记录「为什么这样决定、谁确认、覆盖什么、不覆盖什么」，供产品、开发和测试交接。业务规则统一维护在 [需求基线](REQUIREMENTS.md)，后台验收统一维护在 [后台验收标准](../../admin-web/ACCEPTANCE.md)；本页不再建立另一套功能清单。

## 后续遇到不清楚的需求时

1. 先查需求、当前权威原型、已有领域合同和实际实现，列出冲突原文及来源。区分「文案不同」「规则改变」「代码没做」「尚未测试」，不能把现有代码当需求答案。
2. 复用需求基线已有的 `Q-ADMIN-*` 编号；新问题在基线登记，不另建平行待办。向用户一次说明具体缺项、影响、推荐方案和必要配合，只暂停依赖该决定的工作。
3. 用户明确确认后，在本页追加记录：日期、用户确认原话、最终决定的基线位置、适用端、替代的旧说法和未确认边界。建议、AI 推断和用户确认必须分开写；部分确认不能把整条问题标成关闭。
4. 同步基线、术语、领域合同及对应验收场景；外部原始 PRD/原型快照保留原样，以记录说明新决定覆盖何处。代码另行实现，不能把文档更新记成已修复。
5. 实现后补服务端合同、小程序与后台联动检查，以及真实环境保存、离页重开、独立回读证据。记录 commit、环境、实际验证与未验收项；更新对应需求同一份未定稿的公开验收报告（[本次用户管理草稿](https://miptest.01mvp.com/reports/admin-users-20261020-v1/)），定稿后按 [版本规则](acceptance-site/README.md) 留档。

记录模板：`编号 / 日期 / 状态 / 来源原话 / 基线位置 / 覆盖的旧说法 / 涉及端与数据 / 未决边界 / 实现与验证证据`。状态至少分开「待确认」「部分确认」「已确认待实现」「已实现待验」「已验收」；不把需求确认等同于测试通过。

## Q-ADMIN-09：产品称呼与权限身份分开

**记录日期：2026-10-20。状态：核心规则已确认，例外边界待确认；展示分类尚未按本次决定实现和验收。**

- 用户提供的业务说明：「身份类型只有2种：玩家和嘉宾。但是不同的条件，会出现不同的角色。」「在产品语言和他们对齐就行，游客报名并签到一场活动后成为嘉宾。」用户在解释后回复「嗯，好的，没问题」，并要求将澄清持续记录。
- 最终规则见 [需求基线 §1 身份与访问](REQUIREMENTS.md#1-身份与访问)。服务端会员权限仍为 `GUEST/PLAYER`；产品展示区分游客、嘉宾、玩家。未登录游客是会话状态，不额外创建业务身份。
- 覆盖旧说法：旧 v1 的「仅参加早会后成为嘉宾」改为「报名并签到一场活动」；截图中的「登录后的非会员用户从头到尾都叫嘉宾」不再作为统一产品称呼。原始输入保留，不重写成已经一致。
- 涉及小程序和 Web 后台的标签、列表分类、筛选、统计与导出；分类由服务端真实会籍和活动事实提供。不能仅改文案、从客户端已加载列表判断，或新增第三种权限身份。具体字段和查询结构由工程侧决定。
- 不扩大授权：游客变嘉宾不等于成为玩家或后台人员；签到后的本场互动仍单独校验活动资格，后台角色仍单独配置。
- 尚未确认：签到被撤销后是否退回游客；退款、到期或会籍撤销后的展示称呼是否按历史有效参与重新判断。取消报名、审核未通过、只报名未签到均不满足「报名并签到」条件，但撤销后的历史称呼不能由此自行推断。主分会归属及后台代改字段仍分别属于 Q-ADMIN-06/08，本次未一并确认。

后续验收至少覆盖：未登录游客；已登录无会籍且无签到的游客（权限 `GUEST`）；报名并签到一场非早会活动后的嘉宾（权限仍 `GUEST`）；有效会籍的玩家；入会待审核不提前获得玩家权益；普通注册和签到不授予后台角色。验证新请求/重开页面及列表、筛选、导出一致性。**以上是后续用例，本次没有执行这些新旅程，不能标通过。**

**记录日期：2026-10-20。状态：规则已确认，测试后台入口及权限合同已验证；真实微信新注册和实际人工发放仍待验。**

用户转述甲方：「玩家权益在哪里给 没找到」「新用户进来不能是管理员，不需要有后台角色，后台角色单独配」。现行规则见 [会员领域：用户与后台授权分离](../MEMBERSHIP_DOMAIN.md#用户与后台授权分离)，验收见后台 U04。新注册用户默认不创建后台账号或角色绑定；开通玩家权益不赋予管理权限。

入口和证据见 [玩家权益与角色分离交接](evidence/admin-player-access-20261020/README.md)。测试库现存管理员来自历史显式初始化，不是注册自动授权；不能把入口调整描述为修复了已发现的自动提权漏洞。本次身份称呼澄清不改变这些授权规则。
