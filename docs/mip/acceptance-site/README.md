## 每次任务的交付流程

先遵循 [测试验收与生产发布规则](../../../AGENTS.md#测试验收与生产发布用户2026-10-27确认)。本批先给测试验收页，逐项注明修改成果，并给出对应测试入口、版本、数据环境和未验收边界；等待用户明确确认本批通过并允许上线后，再发布和实际复验生产，提供独立生产报告URL并链接测试记录。两阶段保留各自证据，不覆盖测试报告、不把测试通过改写为生产通过。此流程只补充内容与状态，保留已确定的正文结构、目录和图片交互。

1. 实际修复并验证后，在 `reports.json` 新增报告；同一需求尚未定稿/外发时更新原草稿。未执行、失败、真机待测必须分别写明，不能因测试绿或上传成功而宣称验收通过。
2. 每份报告记录标题、需求标识、版本、草稿/定稿、创建/更新时间、实际验证时间、首次提交时间、代码提交 SHA 与提交时间、环境、验证结论和未验收项。首页按更新时间倒序，以北京时间日期分组，每天合并为一条验收记录，点击直接进入当天重点需求；小修放底部，用短句说明实际改进，必要的待复测简短保留。精确时间、代码SHA等追踪信息保留源数据，不显示在面向客户的正文。
3. `comparisons` 只在界面变化时展示必要的修改前后截图，直接展示；有当前权威原型原图时加原型列，无原型不放占位列。纯功能/性能优化标记 `uiChange: false`，不强制提供截图。截图仍保留来源、环境、视口、角色/样本差异；不得用旧原型、自制图或功能截图充当原型。
4. 只引用已人工检查、可公开的文件，放入对应的 `docs/mip/evidence/`。用户确认内部验收的昵称、头像等普通账号信息后续不再加灰块；密码、密钥、登录凭证、二维码、身份/订单编号及原始云日志不发布，其他敏感信息仍需检查。旧报告的原始证据不随新报告覆盖，已有灰块图不因此重做。
5. `node scripts/acceptance-site.mjs build` 生成隔离输出；检查桌面和390px手机页面、图像解码、内部链接及实际内容。`node scripts/acceptance-site.mjs publish` 发布到既有项目，随后核对真实域名所有文件字节和浏览器画面。
6. 用户明确说“定稿/已经发给客户”后，先核对报告完整，再运行 `node scripts/acceptance-site.mjs freeze <id>` 并提交。定稿内容及图片摘要锁定，后续构建拒绝修改。新需求或定稿后反馈，复制为新的 `id` 和递增 `version`，填写 `previousVersion`，生成新版本；保留旧版本 URL 和时间。

发布异常先回读实际 Pages 部署状态，再决定是否重试；命令失败不代表云端一定未生效。TLS/代理断连先用无凭证请求区分本机出口和平台错误，不据此反复登录、轮转密钥或扩大权限；保持 HTTPS 校验。确需临时调整本机路由时，只覆盖本次目标域名，保存并核对原配置与节点选择，完成后恢复；代理原配置、账号与原始日志不进入仓库或公开站。

图片预览使用非导航按钮，避免脚本尚未就绪时跳离报告；读者脚本与样式 URL 带构建内容摘要。发布后须在真实域名核对版本参数并实际打开弹窗，不能以本地正常或旧脚本的 `reader-ready` 状态替代。

图片外的空白处须可关闭预览；图片本身和缩放/拖动不关闭。关键截图可在对应单元的 `circles` 中填写百分比范围 `{x,y,width,height}`，以独立红色椭圆层标注，缩略图与弹窗一致，原图字节不变；只标有帮助的变化，不强制给历史图补圈。发给甲方前按根 AGENTS 主动提醒验收版本/入口/环境、生产同步情况及仍待手机验证的项目。

2026-10-21 用户最终要求：客户页面一律精简。开头一句目标；甲方需求逐项写要求与实现/验收结果，标准并入对应项，不再重复长原话、目标清单和验收大表。自主小修在底部按项用短句说清具体改进和结论，不用「顺带优化」一笔带过；版本信息一句说明，测试配置、示例海报等不展开。必要的待复测简短保留，详细证据留仓库。`daily-summaries.json` 的 `reportIds` 选择当日重点报告，`otherUpdates` 可用字符串数组，在正文最底部逐项说明其他改进；未选报告与原始证据保留原网址，不因精简删除历史。旧 `request` / `goals` / `acceptance` 仍支持历史页面，新报告默认不用长篇展开。图片使用较小 WebP 预览，点击在本站弹窗查看原图，可放大/适应屏幕、关闭或按 Esc 返回；不另开页面，原图与冻结摘要不变。

`daily-summaries.json` 可编辑当天的简短标题、概述和共同待复测事项；只概括已有证据，不把测试/开发工具结果写成生产或真机验收通过。当天页面直接呈现甲方重点要求及必要画面对照，小修放最底部；原报告URL继续保留。

单项文案可通过 `indexTitle`、`highlights` 与 `pendingSummary` 提炼；它们只概括现有证据，不改写验证结论。当天汇总由报告自动生成至 `/updates/YYYY-MM-DD/`，保留每份报告原始 URL、首次提交时间和冻结规则。

甲方原图不能替代测试环境的修复成果图。需要看界面判断结果的条目，使用 `comparisons` 或 `evidenceImages` 在结果区直接展示真实修复截图；`evidenceTitle` 可标为“测试环境修复结果”。后台配置到小程序的联动，用同一业务对象展示“后台配置 → 小程序结果”，使名称、配置值与实际显示能对应；不重复堆放只证明同一结果的卡片。交互前后状态需注明为同版本操作过程，不能冒充修复前后版本。截图前确认目标路由、页面ready及实际画面一致，舍弃切页尚未完成的旧画面。

`submittedAt` 是该报告首次发布到验收站的时间，`verifiedAt` 是实际验证时间，`commitAt` 是代码提交时间，三者不得混用。草稿后续反馈只更新 `updatedAt`、结论与证据；首次提交时间不变。冻结后不能改标题、时间、结论、图片或锁文件来绕过约束。
