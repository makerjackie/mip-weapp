# MIP 验收标准

验收分为静态、本地行为、运行时、staging 和真机/生产五层。任何一层没有证据时都保留待验收，不能用另一层通过代替。实现与验证的当前状态统一记录在 [COVERAGE_MATRIX.md](COVERAGE_MATRIX.md)。

## 证据原则

- 代码存在只证明实现范围，不证明运行时或外部环境可用。
- 本地测试通过不等于微信开发者工具、真机、staging 或生产通过。
- staging 通过不等于正式 AppID、正式商户或生产数据通过。
- 开发者工具视口不等于真机，也不等于 Mac/Windows 微信客户端。
- `.tmp/` 会被忽略或覆盖，只能用于当次排错；现行结论必须引用仓库可提交证据或可重复的实时读回。
- 证据必须记录日期、环境、代码提交或源码指纹、执行入口、结果和适用边界。
- Demo、TEST 订单和模拟 provider 不能冒充真实会员、真实支付或外部投递。

## 第一层：静态门禁

合并前执行：

```bash
pnpm verify
pnpm admin:web:verify
pnpm verify:all
git diff --check
```

必须满足：

- 页面只经过 modules 与 platform 调用服务端；
- `admin-web/` 不引用 `wx`、WXML、TDesign MiniProgram 或小程序页面；
- 活跃 MIP 代码不读写其他项目前缀；
- 迁移只追加 `mip_*` 对象并写入 MIP 迁移记录；
- 核心部署清单、scheduler 和支付可选函数边界清楚；
- 金额、会员、报名、签到、成长和权限判断具有服务端测试；
- 文档链接、路由清单、迁移 lock 和 operation registry 一致。

通过条件为命令退出码为 0，并记录当次测试数量。测试数量只写入 [PROJECT_STATUS.md](PROJECT_STATUS.md) 的日期化快照，不写入长期规则。

## 第二层：本地行为

每个业务切片至少覆盖：

- 正常、空数据、校验失败、无权限、版本冲突和下游失败；
- AppID、平台/分会/活动 scope 的正向和越权用例；
- mutation 的版本保护、幂等、审计和必要的 outbox；
- 支付、退款、权益、成长、任务完成、游戏币和盲盒的服务端权威事务；
- 双向屏蔽、隐私、敏感字段脱敏和独立 capability；
- Web BFF 的 principal、来源、请求体、字段白名单和 CSRF 边界。

本层通过只记为 `verified-local`。

## 第三层：运行时

### 微信小程序

执行入口：

```bash
pnpm runtime:preflight
pnpm test:runtime
```

验收至少包括：

- `config/runtime-pages.json` 中全部路由可达；
- 四个主 Tab、深链、返回和身份补全后恢复原动作；
- loading、empty、error、forbidden、conflict、disabled 代表状态；
- 375px 代表视口和长内容下无裁切、重叠或不可达操作；
- 活动、机会、档案、任务、成长、游戏、知识和管理端代表旅程；
- 与 [FIGMA_MAP.md](FIGMA_MAP.md) 的代表 frame 同尺寸对照；
- 运行时与 IDE 编译诊断无失败。

完整报告若要支撑现行文档结论，应把摘要和必要截图保存到 `docs/mip/evidence/<date>/`。只存在 `.tmp/` 的报告不得标记为仓库可复核通过。

### React Web 管理端

至少验证 390×844、1280×720 和 1440×900：

- 登录 challenge、确认、会话恢复、退出和撤权后立即失效；
- 14 个一级页面及适用详情的加载、空态、错误和无权限状态；
- 筛选、分页、抽屉/详情、写操作成功、版本冲突和结果不明确后的刷新；
- 键盘操作、窄窗降级、敏感操作确认和错误恢复；
- BFF 真实失败时显示错误，不回退演示数字。

## 第四层：staging

当前 staging 基线值见 [PROJECT_STATUS.md](PROJECT_STATUS.md)。环境变更后必须重新取得以下证据：

- 迁移版本、顺序、校验和与 lock 一致，幂等复跑无漂移；
- MIP runtime 账号只有当前 migration lock 目标表的必要权限，无 schema-level ALL 和全局 DELETE；
- 核心函数、scheduler 和支付可选函数按各自清单读回，不能把函数目录当作已部署；
- AppID、函数名、HMAC、对象前缀和环境白名单一致；
- 消息与知识 scheduler 分别只有自己的滚动单次 timer，无 MySQL/VPC，角色与密钥不共用；
- `cloud:verify`、健康检查和客户端调用权限符合预期；
- Demo 只写当前 AppID 下的 `mip_*` 表，不产生真实支付、真实会员或其他项目数据。

## 第五层：真机与生产

以下能力必须取得对应环境证据：

| 能力 | 必需证据 |
| --- | --- |
| 微信身份与手机号 | 正式 AppID 下首次登录、授权拒绝、换绑和重复手机号拒绝 |
| 支付与退款 | 正式商户下单、调起、回调验签、查单、权益生效、退款和幂等重放 |
| 扫码签到 | 真实小程序码、登录/报名/支付恢复、过期码、重复签到和现场边界 |
| 媒体 | 选择、上传、内容安全、临时 URL、失败清理、相册保存和不同用途绑定 |
| 原生能力 | 地图、日历、拨号、录音、分享、订阅消息、视频号和 `web-view` |
| 外部 provider | AI、内容采集、客服/服务号和通知的限流、失败、审计与回执 |
| 客户端兼容 | iOS/Android 真机以及 Mac/Windows 微信发布版本 |
| Web 生产 | 真实管理员、真实 API、关键 mutation、敏感导出、错误恢复和审计 |

生产证据必须采用最小必要数据，不在仓库记录手机号、OpenID、Cookie、授权头、商户密钥或完整敏感导出。

## 领域最低验收

| 领域 | 最低闭环 |
| --- | --- |
| 身份与档案 | 首登、协议、资料、隐私、手机号、公开档案和来源动作恢复 |
| 会员与订单 | 方案、订单意图、支付待确认、ledger 终态、权益和退款 |
| 活动 | 列表、筛选、详情、报名、支付、签到、参与人、相册、心动和反馈 |
| 机会与协作 | 发布、团队、引荐、兴趣、评论、案例、撮合、屏蔽和通知 |
| 成长、任务与游戏 | 服务端奖励、余额流水、等级、勋章、任务资格、赛季、排行和盲盒事务 |
| 知识内容 | 来源、计划、采集、审核、免费/会员/单内容访问、评论和退款边界 |
| 消息 | outbox、站内信、偏好、收件人快照、定时、失败复核和外部回执 |
| 管理端 | capability、scope、脱敏、导出、审计、双端一致性和 Web principal |

领域实现与验证状态只在 [COVERAGE_MATRIX.md](COVERAGE_MATRIX.md) 更新，避免再次生成平行的验收状态表。
