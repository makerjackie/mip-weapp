# 管理后台登录链路验证

适用于旧 Cloudflare 后台迁入 CloudBase 后，密码、六位登录码或二维码确认失败的排查。先审计和拉取最新代码，按调用链检查两端、BFF、管理云函数及认证存储，不先改密码或替换全部回调。

## 密码与账号

- 旧 D1 与新 MySQL 认证存储是独立的。读取账号存在性、创建时间和已配置迁移范围，报告只保留数量与是否存在，不输出手机号、微信身份、密码哈希或 pepper。
- 使用已配置且获授权的测试账号验证旧、新 origin 的真实登录、管理会话和退出。测试账号通过不证明用户报告的另一个账号已通过；未拿到该账号标识时明确待核对。
- 密码哈希依赖各站自己的 pepper，不能直接复制。现有单维护者迁移有源账号数守卫；源站出现多个账号后不能绕过守卫批量导入或随意重跑。
- 有管理权限的用户可用自己的微信确认新后台登录，再在账号菜单“设置 / 修改登录密码”。修改凭证交给用户本人完成；不得给未知账号重置密码、借用维护者身份或新增权限。

## 小程序确认与回调

1. 回读管理 API 和 BFF 的配置，核对旧站确认 URL、新站 migration URL、HMAC 对应关系和 QR 环境；不输出秘密值。同步云端和本机覆盖配置，防止下次部署回退。
2. 核对当前实现的命名空间：CloudBase 的 `9xxxxx` 六位码与 `z_` scene token 分流到 migration 回调，旧站拒绝这些保留范围；其余旧码仍走旧确认 URL。以本次源码为准，不把所有确认发送到同一个站。
3. 由真实网页创建 challenge，在已登录且有管理员权限的小程序客户端输入其六位码，点击现有确认按钮。浏览器等待自身 challenge cookie 对应的确认，取得真实会话并展示非空业务数据，再退出。
4. scene 流程同样使用真实 challenge、真实小程序页面与按钮。不要伪造确认主体或只用签名请求替代微信身份。BFF 成功消费确认后的轮询状态是 `AUTHENTICATED`；单次消费、cookie 绑定和超时会让已用 challenge 失效，不重复消费后再判定失败。
5. 旧、新入口分别测确认、会话和退出；二维码图片生成只证明生成接口工作。微信开发者工具调用真实云函数与手机实际扫码是两层证据，不能互相替代。

后台域名提示从 `brand.adminConsoleDomain` 读取。显示文案更新需随下一次微信版本发布，后台回调修复不依赖重新上传小程序。上传仍执行仓库完整门禁并遵循当次授权范围。

## 登录后的读取

验证来源拒绝、错误密码、Secure/HttpOnly/SameSite cookie、退出后会话拒绝，以及查询 allowlist 内各模块的非空 DTO。列表修复要验证真实页面、中文筛选、空结果与分页合同；不能把 HTTP 200 或空数组当作业务成功。

出现仅非空列表失败时，检查 SQL 并发与池队列。每行并发加载两项关联会把整页变成大量查询；按 app 作用域批量读取、按稳定键分组，保持排序、金额与分页合同。回归测试应先能复现实际队列边界，再验证查询数量与 DTO 隔离；不为了压测写生产业务数据。

执行记录放入 `docs/mip/evidence/`，只提交脱敏检查与摘要；账号、cookie、scene、原始环境、日志和截图放在忽略的私有目录。全流程读取通过不代表所有新增、支付、权限变更和真机场景已验收。
